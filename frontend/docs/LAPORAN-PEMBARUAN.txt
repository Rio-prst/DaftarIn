A. Masalah 1 — Berkas Tidak Benar-Benar Tersimpan & Keterikatan Draf Asal:
   - Penyebab pada kode sebelumnya:
     Di `PreparationDocsPage.tsx`, validasi mengizinkan file sampai 5 MB, tetapi hanya file `<= 1,5 MB` yang dibaca dengan `FileReader`. File `1,5 MB–5 MB` langsung memanggil `addDocument({ status: "TERUNGGAH" })` tanpa menyimpan isi berkas sama sekali. Selain itu, hasil `saveSharedFilePreview()` tidak diperiksa dan blok `reader.onerror` tetap memanggil `addDocument({ status: "TERUNGGAH" })` serta menampilkan toast sukses. `addDocument()` juga hanya memperbarui `activePreparation` saat callback selesai tanpa mengikat `targetPrepId` asal saat tombol pilih file diklik.
   - Perbaikan:
     * Membuat modul penyimpanan berkas browser berbasis **IndexedDB Blob** (`frontend/src/utils/fileStorage.ts`, database `daftarin_file_storage_v1`, store `file_blobs`) yang mendukung ukuran penuh hingga **5 MB** (`MAX_UPLOAD_FILE_BYTES = 5 * 1024 * 1024`) tanpa menyimpan PDF/gambar besar sebagai Data URL di dalam satu objek JSON `localStorage`.
     * Fungsi `readAndStoreUploadedFile()` membaca `ArrayBuffer`, menyimpan `Blob` ke IndexedDB, dan memverifikasi keberadaan serta ukuran `Blob` di IndexedDB sebelum mengembalikan sukses.
     * `PreparationDocsPage.tsx` menangkap konteks asal (`prepId`, `slotId`, `nextVersion`, `existingDocName`) pada `uploadContextRef` tepat saat warga menekan "Pilih berkas" / "Ganti berkas", lalu meneruskan `ctx.prepId` ke `addDocument(doc, ctx.prepId)`. Jika warga berpindah draf saat file sedang dibaca, berkas tetap masuk ke draf dan slot asal.
     * Jika pembacaan atau penyimpanan gagal, aplikasi menampilkan banner dan toast error yang dapat ditindaklanjuti, **tidak** memasukkan metadata `TERUNGGAH`, dan **mempertahankan berkas versi lama** pada slot tersebut.
     * `computePreparationReadiness()`, `submitForOfficerReview()`, dan `resubmitApplication()` memvalidasi `unavailableRequiredDocs.length === 0` serta `isDocumentContentAvailable(doc)` sebelum mengizinkan pengiriman permintaan atau revisi.

B. Masalah 2 — Pratinjau Berkas Kiriman Terhapus / Tertimpa / Salah Klasifikasi Contoh:
   - Penyebab pada kode sebelumnya:
     Di `DocumentPreviewModal.tsx`, `saveSharedFilePreview()` memotong entri lama dengan `.slice(-8)` sehingga berkas kiriman aktif terhapus setelah 8 unggahan. Selain itu, `isSampleBroken` dan `isSampleFixed` menggunakan pencocokan substring nama file (`fileName.includes("contoh")`, `"terpotong"`, `"simulasi"`, `"fixture"`), sehingga berkas asli warga bernama `contoh-kk.pdf` apabila kehilangan pratinjau justru dirender sebagai lembar dokumen simulasi palsu.
   - Perbaikan:
     * Menghapus batas pemotongan 8 entri. Setiap unggahan versi baru (`v1`, `v2`, dst.) disimpan di IndexedDB dengan kunci unik per versi (`file-<prepId>-<slotId>-v<version>-<timestamp>-<rand>`). Mengganti berkas pada draf membuat entri `v2` baru tanpa menimpa `Blob` `v1` yang direferensikan oleh `submitted_snapshot` atau `submission_history` (`Kiriman #1`).
     * Menambahkan fungsi `isBuiltInSampleDocument(doc)` dan `isCroppedSampleDocument(doc)` di `DocumentPreviewModal.tsx` yang **hanya** memeriksa metadata eksplisit (`doc.qualityPreset !== "user_file"` serta `doc.fixtureId` / `doc.qualityPreset === "sample_issue" | "sample_clean"`), tanpa pemeriksaan substring nama file sama sekali.
     * Berkas unggahan warga (`qualityPreset: "user_file"`) bernama `contoh-kk.pdf` selalu menampilkan isi `Blob` asli warga, atau jika `Blob`-nya tidak tersedia menampilkan peringatan jujur **"Berkas tidak tersedia"** beserta tombol pilih ulang berkas (untuk warga) atau tombol tandai **"Belum dapat diperiksa"** & minta perbaikan (untuk petugas).

1. RINGKASAN RANCANGAN ALUR DAN PERUBAHAN ARAH PRODUK
--------------------------------------------------------------------------------
- Dasar referensi pelayanan Kartu Keluarga (KK):
  Mengacu pada pola prosedur layanan KK daerah (Disdukcapil Kota Pekalongan https://disdukcapil.pekalongankota.go.id/halaman/penerbitan-kartu-keluarga.html dan Disdukcapil Kab. Ponorogo https://dukcapil.ponorogo.go.id/persyaratan-mengurus-kartu-keluarga-kk/):
  1) Warga menyiapkan formulir dan persyaratan sesuai kondisi permohonannya.
  2) Petugas memeriksa kelengkapan dan kesesuaian berkas.
  3) Kekurangan dikembalikan dengan arahan perbaikan terstruktur.
  4) Berkas yang sesuai diteruskan untuk pengajuan/pengolahan di kanal resmi.
  5) Hasil diserahkan melalui kanal pelayanan resmi yang berlaku.
  Seluruh antarmuka DaftarIn menegaskan bahwa aplikasi ini adalah pendamping persiapan & tinjauan awal, bukan sistem SIAK pemerintah dan tidak berwenang menerbitkan dokumen resmi.

- Pemisahan Validasi Dasar, Tinjauan Petugas, dan AI/OCR:
  1) Validasi dasar aplikasi: memeriksa konfirmasi kebutuhan (Tahap 1), format isian wajib pemohon (Tahap 2: Nama, 16 digit NIK, 16 digit Nomor KK, alamat, alasan), serta keberadaan berkas persyaratan wajib dengan format PDF/JPG/PNG dan ukuran <= 5 MB (Tahap 3).
  2) Tinjauan petugas: pemeriksaan isi dan keterbacaan dokumen serta kesesuaian data oleh petugas pendamping setelah draf dikirim oleh warga.
  3) Analisis AI/OCR: ditunda sebagai kemampuan tambahan berikutnya. Belum tersedianya OCR/LLM atau penggunaan berkas perangkat warga (user_file) tidak lagi menghalangi pengiriman berkas maupun pengiriman perbaikan. Adapter evaluatePreparationDraft() tetap dipertahankan untuk integrasi berikutnya.

- 4 Tahap Pra-Pengiriman Warga:
  Stepper persiapan disederhanakan menjadi:
  1. Kebutuhan (/persiapan/kebutuhan) -> 2. Data (/persiapan/data) -> 3. Dokumen (/persiapan/dokumen) -> 4. Tinjau & kirim (/persiapan/ringkasan).
  Pekerjaan petugas setelah pengiriman ditampilkan pada halaman Status Tinjauan & Pelacakan (/pelacakan), bukan sebagai langkah di dalam form persiapan warga. Route /persiapan/pemeriksaan tetap dipertahankan sebagai halaman rincian validasi & simulasi aturan opsional agar tautan lama tidak rusak.

- Pemisahan 3 Entitas Status:
  1) Draf persiapan pribadi warga (PREP-2026-XXXX) — tetap privat sampai dikirim eksplisit.
  2) Permintaan tinjauan awal DaftarIn (TINJAU-2026-XXXX) — dikirim ke Unit Tinjauan Pendamping Adminduk (petugas contoh Budi Santoso) dengan status: Belum dikirim, Menunggu tinjauan, Sedang ditinjau, Perlu perbaikan, Perbaikan dikirim, dan Tinjauan awal selesai.
  3) Catatan pengajuan di kanal resmi pemerintah (Dicatat warga / Hasil layanan diterima warga) — dicatat ketika warga sudah mengajukan berkas di loket Disdukcapil, MPP, atau portal resmi daerah.

RINGKASAN
Pembaruan ini memperbaiki arsitektur data persiapan dan pemeriksaan di DaftarIn agar setiap urusan warga berdiri sendiri dengan ID unik (PreparationRecord), menghapus penyimpulan kualitas berkas berbasis nama file atau nomor versi, menyatukan aturan perpindahan antar 5 tahap persiapan, mengamankan proses pemeriksaan ber-timer dari perubahan state di tengah jalan, mempertahankan konteks pilihan tamu saat login/daftar, serta mengikat alur revisi pengajuan langsung ke ID persiapan yang tepat.

MASALAH YANG DIPERBAIKI
1. Data formulir pemohon (formData), dokumen (documents), dan hasil pemeriksaan (inspections) sebelumnya disimpan sebagai satu objek global per akun, sedangkan metadata persiapan menggunakan serviceId sebagai kunci. Akibatnya dua pengurusan untuk layanan yang sama (misalnya dua pembaruan KK untuk anggota keluarga berbeda) saling menimpa. Kini setiap persiapan disimpan sebagai objek PreparationRecord mandiri dengan ID unik (prep-...) dan referensi unik (PREP-2026-XXXX) di dalam daftarin:<userId>:preparations:v3.
2. Pemeriksaan berkas sebelumnya menyimpulkan kualitas dokumen dari nama file (terpotong/buram) dan menganggap setiap dokumen versi > 1 otomatis utuh/selesai. Kini nama file dan nomor versi tidak lagi dijadikan bukti keterbacaan isi dokumen. Pemeriksaan dipisahkan menjadi 4 cakupan eksplisit: format_formulir, keberadaan_berkas, analisis_isi_dokumen (berlabel Simulasi Fixture untuk preset contoh vs Belum dianalisis otomatis untuk berkas pengguna), dan aturan_admin (dicatat sebagai belum dievaluasi otomatis bila belum memiliki evaluator).
3. Tahap 2 (PreparationDataPage) sebelumnya memanggil confirmNeedStep() secara diam-diam sehingga pengguna dapat melewati Tahap 1 tanpa konfirmasi. Auto-confirm tersebut telah dihapus; prasyarat setiap tahap kini divalidasi secara terpusat di computePreparationReadiness().
4. Validitas pemeriksaan (InspectionSnapshot) kini membandingkan sidik jari data (dataSignature), dokumen (docSignature), versi dan rincian syarat panduan layanan (guideSignature), serta rincian isi aturan aktif admin (rulesSignature), bukan sekadar menghitung jumlah aturan aktif.
5. Proses runAIScanSimulation() (timer 700ms) kini dikunci per ID persiapan yang sedang dipindai, menangkap snapshot input saat mulai, menolak klik ganda pada persiapan yang sama, dan mengabaikan hasil apabila data/dokumen diubah sebelum timer selesai.
6. Pilihan layanan, wilayah, dan kondisi dari halaman panduan publik sebelum login kini disimpan di sessionStorage (daftarin:guest-intent:v1) dan parameter URL (?new=1&service=...&condition=...), serta diizinkan oleh permittedReturnPath() saat melewati halaman Masuk atau Daftar.
7. Revisi pengajuan pada TrackingPage dan PreparationSummaryPage kini terhubung ke preparation_id spesifik (mis. sample-kk-01 terhubung ke prep-sample-kk-01), dan status PERLU_DITINJAU ditangani secara eksplisit pada halaman Ringkasan.
8. Metadata panduan layanan contoh kini diberi penanda jelas bahwa tautan rujukan mengarah ke portal umum dan standar layanan lokal belum diverifikasi otomatis oleh instansi daerah.
