B. PRIORITAS 0 — KONTRAK INTI DAN KEAMANAN DATA

B1. Bedakan tinjauan pendamping dari pengajuan instansi
Saat ini endpoint petugas memakai status pengajuan generik. Notifikasi
completed bahkan masih menyebut pengajuan resmi selesai. Itu tidak sesuai
cakupan DaftarIn jika event hanya menutup tinjauan awal.
Diperlukan:
- Jenis catatan eksplisit: tinjauan pendamping atau laporan pengajuan instansi.
- Status tinjauan dan status pelaporan resmi terpisah, dengan sumber/aktor.
- Tidak menciptakan nomor resmi pemerintah dari nomor internal DaftarIn.
- Pelaporan warga tetap bertanda dilaporkan warga/belum dikonfirmasi instansi.
- Selesai tinjauan tidak berarti dokumen resmi terbit atau hasil diterima.
- Kanal, nomor tanda terima, waktu pengajuan, bukti opsional dan catatan hasil
  penerimaan di instansi harus tersimpan sebagai objek terpisah.
SUDAH ADA: pencatatan pengajuan warga dengan sumber CITIZEN_REPORT dan label
belum terkonfirmasi instansi; endpoint confirm-result-received juga sudah ada.
DTO konfirmasi hasil kini hanya received_at/note opsional. Lengkapi kanal,
konfirmasi eksplisit, validasi urutan status dan idempotency pada endpoint itu;
jangan meminta tim membuat endpoint konfirmasi hasil kedua.
Uji terima: petugas menyelesaikan tinjauan -> warga masih punya tindakan ke
instansi -> warga mencatat pengajuan/hasil; ketiga tahap tidak saling tertukar.

B2. Snapshot kiriman yang tidak berubah
Detail petugas saat ini berisi layanan/instansi/nama warga/timeline; belum
mencukupi layar pemeriksaan frontend. Tambahkan kontrak kiriman/revisi yang
mengembalikan:
- preparation_id, application_id, internal_reference, submission_version.
- Snapshot layanan, guide_version_id, condition_key, region/agency/channel.
- Required document slots yang berlaku saat warga menyetujui kiriman.
- Data pemohon, identitas pengurus, subjek keluarga dan deklarasi pendampingan.
- consent_version/consented_at, submitted_at, citizen_note/changes_summary.
- Lampiran yang merujuk document_version_id tetap, bukan latest document.
- Daftar versi kiriman dan keputusan petugas pada masing-masing versi.
Usulan: POST /preparations/:id/submissions; POST /applications/:id/resubmissions;
GET /applications/:id/submissions; GET /applications/:id/submissions/:version.
Uji terima: warga mengedit draf/unggah versi baru setelah kirim -> petugas tetap
melihat salinan lama sampai warga benar-benar mengirim revisi baru.

B3. Penilaian per isian/berkas dan revisi terstruktur
POST officer events sekarang belum membawa penilaian per item. Diperlukan:
- submission_version + expected_version dan decisions/itemAssessments.
- itemId, itemType form_data/document, verdict sesuai/perlu_perbaikan/
  belum_dapat_diperiksa, note, document_version_id/fileVersion bila berlaku.
- Slot wajib yang tidak terlampir tetap masuk evaluasi, bukan dilewati.
- Setiap masalah punya catatan spesifik, target perbaikan dan arahan tindakan.
- Keputusan selesai ditolak bila item wajib belum dinilai atau masih bermasalah.
- Revisi warga membentuk versi baru; penilaian lama tetap terbaca di sejarah.
- Draf penilaian petugas harus bisa disimpan tanpa langsung mengirim keputusan.
Usulan: PUT /officer/applications/:id/evaluation-draft;
POST /officer/applications/:id/decisions; GET detail mengembalikan semua item.
Uji terima: berkas KK salah -> hanya slot/versi KK itu ditandai -> warga melihat

B4. Transisi status, konflik dan pengiriman ganda
Temuan source: OfficerService menghitung allowed_actions untuk tampilan, tetapi
createEvent tidak memakainya untuk menolak perpindahan status yang tidak sah.
Diperlukan:
- Transisi divalidasi di server, bukan hanya menyembunyikan tombol di browser.
- Petugas hanya bertindak saat penugasannya masih aktif dan versi kiriman benar.
- Kasus ditarik/selesai atau sedang menunggu klarifikasi tidak bisa diputuskan.
- expected_version/ETag pada edit, penilaian, penugasan, publikasi dan revisi;
  transaksi atomik, respons 409 ketika client sudah tertinggal.
- Idempotency-Key untuk kirim, kirim revisi, keputusan, penarikan dan unggah
  retry. Request yang sama tidak membuat versi/event/notifikasi ganda.
- data_version dan nomor versi dokumen jangan read-then-write tanpa proteksi.
- Idempotency dicakup actor+operasi; payload berbeda pada key sama harus ditolak.
Uji terima: dua tab/two officer -> satu keputusan sah; yang lama mendapat 409.
Retry setelah jaringan putus menghasilkan satu tanda terima dan satu notifikasi.

B5. Upload privat Supabase Storage
Sudah ada adapter; lengkapi/cek:
- Deteksi MIME isi berkas (FileType.fromBuffer), whitelist PDF/JPEG/PNG dan

- Object key unik per versi; hindari overwrite/upsert pada nomor versi balapan.
- DB object metadata dan kegagalan upload mempunyai cleanup/recovery yang jelas.
- Signed URL singkat setelah auth/ownership/penugasan diperiksa. Bucket privat.
- Petugas lama kehilangan akses isi berkas setelah tugas dialihkan; metadata

- Reuse menyalin atau membuat referensi versi milik owner yang terotorisasi;

Uji terima: ID berkas milik warga lain ditolak; signed URL bukan URL publik;

D. INTEGRASI CHATBOT YANG SUDAH DIKERJAKAN
Aktif pada backend lokal: GET /api/chat/status; POST /api/chat/messages.
Request: {query: string(max1000), serviceId?: 1..6,
 history?: [{sender: user|bot, text: string(max1500)}](maks4)}.
Respons sukses: {data:{text, actionSteps, legalCitations, quickAction?,
 source: ai, modelUsed}}. Tidak menerima formData, file, NIK profil atau tools.
400 = payload tidak sesuai; 429 = rate limit; 503 = provider belum siap/gagal.
FE fallback lokal ditandai; bukan menjadikan error provider sebagai kelulusan.

YANG HARUS DIISI AGAR AI LIVE
Masukkan hanya di backend/.env lokal/private deployment secret:
CHAT_AI_PROVIDER=openai_compatible     (atau gemini; disabled untuk nonaktif)
CHAT_AI_API_KEY=<key penyedia>
CHAT_AI_MODEL=<ID model tepat dari penyedia>
CHAT_AI_BASE_URL=<base URL OpenAI-compatible, tanpa /chat/completions>
Untuk Gemini URL sudah ditentukan adapter; isi provider/key/model yang sesuai.
Untuk Claude lewat pihak ketiga, pastikan gateway menyediakan format OpenAI
chat/completions; native Anthropic API belum dibuatkan adapter terpisah.
Restart backend setelah konfigurasi. Jangan commit .env atau kirim key di chat.
VITE_API_URL=/api menuju reverse proxy/proxy lokal; VITE_AUTH_MODE tidak
mengubah tempat key. Frontend tidak memakai secret provider apa pun.

PENGERJAAN CHAT SEBELUM PUBLIK
- Uji provider/model sungguhan; pastikan mendukung format JSON/system message,
  max_tokens dan error sesuai adapter. Pengujian sekarang memakai mock.
- Hubungkan corpus ke panduan admin yang benar-benar terbit/versi/wilayahnya;
  panduan bawaan saat ini tidak otomatis berubah ketika admin memublikasikan.
- Batas biaya/per-user, penanggulangan abuse guest/shared IP dan penyimpanan
  rate limit lintas replika bila deployment memakai beberapa instance.
- Nama penyedia, kebijakan retensi percakapan dan persetujuan penggunaan data
  harus jelas sebelum dipakai publik. Jangan menjanjikan zero retention
  tanpa kesepakatan penyedia. Logging jangan menyimpan key/NIK/isi KTP.
- Injeksi prompt dibatasi lewat validasi, tidak ada tools, pemisahan data dan
  sumber/action tepercaya. Teks model tetap perlu evaluasi jawaban keliru.
- AI pemeriksaan isi dokumen/OCR tetap modul terpisah pekerjaan teman; chat
  tidak otomatis memperoleh akses berkas hanya karena sama-sama memakai AI.
